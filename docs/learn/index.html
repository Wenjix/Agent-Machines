How Agent Machines actually works

Most AI products are a chat window: ask, answer, close the tab, everything resets. This codebase ships something else — a persistent worker on a real computer, deployed in one click onto whichever cloud and with whichever agent brain you choose. This manual teaches the system the way an architect would whiteboard it: each chapter is one idea, the trade-off that forced it, and a simulation you can poke.

00
chapter 00 · the premise

Renting a worker, not a conversation

Start with the problem statement from the project's own vision doc: “People don't want a bare sandbox. They want a worker that audits code, runs on a schedule, and gets smarter over time.” A chat product forgets you when the tab closes. A bare sandbox is an empty Linux box — powerful, and useless until an expert moves in. Agent Machines is the layer between: it deploys the employee, not the desk.

The mental model the explainer uses: the difference between texting a smart friend once and hiring an employee who has a desk, a login, a to-do list, and keeps working when you are not watching. The product is everything that turns a rented computer into that employee.

first principle The value is not the model. It's the plumbing: bootstrapping agents on arbitrary clouds, keeping keys sane, streaming live terminals through hosting never designed for it — built once, as the product.
compare the two rentals

a chat tab

  • resets when closed — no memory of the work
  • no disk, no schedules, no real tools
  • procedures can't accumulate or be exported
  • one vendor's UI, one vendor's cloud

an agent machine

  • persistent Linux box — files, memory, identity survive sleep
  • cron schedules, 161 skills, 30+ integrations, a browser
  • every solved task can become a SKILL.md playbook on disk
  • pick the brain and the cloud; swap either later

chapter 01 · the core idea

Dual routing: two axes, zero lock-in

Every competitor makes you choose a cage: their runtime or their cloud. The core architectural bet here is that both choices are routing decisions, made independently, at deploy time. One axis picks the brain — Hermes, OpenClaw, Claude Code, or Codex. The other picks the floor it stands on — Dedalus, E2B, Sprites.dev, or Vercel Sandbox.

The analogy the repo leads with: OpenRouter for agents and containers — one account routes which runtime and which substrate the way OpenRouter routes models. The companion analogy is “Vercel on AWS”: be the product layer; treat infrastructure as interchangeable. Even the best-performing substrate (Dedalus, ~250ms boots) is explicitly “a competitive default, not the product.”

why two axes is defensible Lock-in on either axis is a moat someone else owns. Routing both keeps the value in what this repo builds: the harness, the control plane, and observation.

chapter 02 · the unit of deployment

The worker: one deployable unit

What actually lands on the box is not “an agent.” It is a composed unit: runtime + skills + MCP servers + integrations + cron + observation, assembled at bootstrap into the worker's home directory, ~/.agent-machines/. That home is the worker's identity — it's what persists through sleep, and what makes the machine this employee rather than a blank box.

The capability surface is deliberately a registry-driven harness with six layers, not a hardcoded tool list. Click each layer below. The strategic one is L1: skills are procedures on disk, so they compound — the vision doc's argument for why you can't get this from a chat product is that “custom playbooks stack up and cannot be exported.”

03
chapter 03 · the core abstraction

One interface, four floors

Here is the classic computer-science move that makes dual routing real: every substrate hides behind one interface, MachineProvider, with seven methods — provision / state / wake / sleep / destroy / exec / streamExec. The rest of the system — dashboard, bootstrap, cron, terminal — is written against the interface and is therefore provider-agnostic. Adding a fifth cloud means writing one adapter, not touching the product.

Two design subtleties worth teaching. First, exec is the load-bearing primitive: if a substrate can run a command, everything else can be built on top of it. Second, capabilities are tiered, not assumed: where a provider has native streaming the system uses it; where it doesn't (Dedalus), it degrades to polling — the UI works either way.

interface as strategy Polymorphism is usually a code-hygiene argument. Here it is the business model: the interface is what makes substrates interchangeable, and interchangeable substrates are what make the product the layer that matters.

chapter 04 · the lifecycle

Deploy → Bootstrap → Attach → Talk

The flagship flow turns “I want a worker” into a live terminal in roughly two and a half minutes (a real measured bootstrap: ~151s). Step through it below — and then turn on the hazards, because every phase carries a scar from a real failure. Three lifecycle principles to hold onto:

Fail closed at the gate. Deploy is blocked until substrate keys and the model router are configured — provisioning must never silently half-succeed. Define success by the health check. Bootstrap is “succeeded” the moment the gateway URL answers /v1/models — not when the installer script says so; everything after runs best-effort. Sleep is the economy. A parked worker costs no compute but keeps its disk, skills and memory; wake re-verifies the gateway and repairs if the substrate reset anything.

05
chapter 05 · the crown jewel

The inversion: a terminal where one cannot exist

The best agent tools are full-screen terminal programs. Most people who'd benefit have never opened a terminal. The obvious bridge — a browser terminal — has an obvious design: hold a WebSocket open from browser through your API to a remote PTY, like SSH-in-a-tab. And on a serverless control plane it cannot work: Vercel functions die at ~110 seconds, cold-start, and have no sticky sessions. A phone call that must never hang up, routed through an operator who goes home every two minutes.

The fix is the repo's signature idea — stateless courier, stateful worker. Stop hosting the session in the API. The session lives on the box: a tmux session holds the real PTY and scrollback. Input becomes a short HTTP POST that execs tmux send-keys -H (hex bytes, serialized so keystrokes never reorder). Output becomes an unbuffered tail -f on a pipe-pane log, streamed back over SSE. The dashboard is a dumb, retryable courier — and the only substrate primitive required is exec, which is why the same terminal works on all four clouds.

the transferable pattern “Serverless browser terminal” is a general solution any SaaS with remote workers could reuse — the closest predecessor is AWS CloudShell, locked to one cloud. The missing primitive was never a better chat UI; it was inverting where the session lives.

chapter 06 · operating the fleet

The control plane: six rooms, two audiences

The dashboard is organized as six surfaces — explore them below. Two cross-cutting ideas matter more than any single screen. Observation before orchestration: usage, cost, activity and bootstrap phase are first-class, because you can only orchestrate what you can see. And one identity gate: every dashboard API first resolves the effective user (verified across 26 route handlers in this repo's knowledge graph) and fails closed with a 401 — never a crash — when there isn't one.

The audiences are sequenced: humans first (route, provision, supervise from the dashboard), agents second — the stated endgame is an MCP + CLI surface so a head agent can provision, route, observe and tear down workers programmatically. The control plane you're learning is designed to eventually be operated by the things it deploys.
